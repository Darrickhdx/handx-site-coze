## 1. 一句话定义

**这是“鉴真小秃驴”的个人 IP 主站；用 AI × 硬件 × 行业产品的真实经验建立信任，以“寻找苏开元”这个家族史项目展示其方法、内容能力与长期作品。**

它不是单一的苏开元档案站，也不是纯技术博客，更不是把研究后台直接摆给普通读者看的数据库。

苏开元项目是全站最不可替代的内容锚：从一份 1936 年文献出发，把家族记忆、历史材料、知识图谱、小说、AI 工作流和后续媒体内容串成一个读者能进入的故事世界。

### 当前应服务的四类人

| 人群 | 他们为什么来 | 首选入口 | 希望带走什么 |
| --- | --- | --- | --- |
| AI／产品合作对象 | 判断站主能否解决真实产品问题 | `/` → `/ai` → `/about#contact` | 专业判断、案例感、可合作性 |
| 历史／故事读者 | 被一个人物谜题和时代故事吸引 | `/discover/1936-pingdiquan` → `/sukaiyuan` | 一个有悬念、能继续追下去的故事 |
| 家族史实践者 | 学习怎样用 AI 整理自己的资料 | `/studio/diagnosis` → `/discover/ai-family-history` | 一套可信、尊重隐私的方法 |
| 研究型读者 | 核对人物、事件和来源 | `/graph`、`/archives`、`/wiki` | 可深挖的条目、定位与关系 |

## 2. 设计总原则

### 2.1 内容要先抓住人，再给材料

现有设计已经从“研究仪表盘”转向“故事先行、材料可追溯”。读者的第一屏应当依次感受到：

1. 一个明确的人、瞬间或问题；
2. 一句让人愿意往下看的标题；
3. 一个可进入的故事入口；
4. 当读者想核对或继续探索时，再给出原文、图谱、定位和研究细节。

正确示例：

> “一行旧字，把我带回曾祖父的名字。”

不应把这类表达放在首屏：

> “来源 ID 完整保留”“body-verified”“迁移映射”“独立来源数”。

这些仍然重要，但应进入“研究定位”“继续深挖”或展开区，不抢走普通读者的第一次阅读体验。

### 2.2 严谨不等于冷硬

对史料的尊重必须保留，但页面语言要翻译成阅读语言：

- “body-verified” → “这一段原文已经核对过”；
- “metadata-only” → “我们先看见了目录线索”；
- “local copy status” → “本站保留的是阅读线索”；
- “不能推出” → “这一页还不能替我们补完的故事”。

结论边界应当以小字提示、展开详情、来源链接和“还想继续追问”出现，而不是以警告卡墙、工程字段和密集编号淹没页面。

### 2.3 主站与专题要彼此增益

个人 IP 是主叙事，苏开元是旗舰项目：

- 主站证明站主是谁、做过什么、为何有能力做这项复杂工程；
- 苏开元项目证明站主不是空谈 AI，而是真正在整理、核对、写作和搭建系统；
- 小说与媒体内容将来负责扩大传播；
- 图谱、Wiki 与档案页负责建立深度与可信度。

不要把“研究安全门禁”误当成全站的内容主角，也不要把小说或家族回忆反向写成已经确认的历史事实。

## 3. 当前信息架构

### 3.1 一级导航：保持克制

全站 Header 当前仅保留四个入口和一个合作 CTA：

| 一级入口 | 页面 | 目的 |
| --- | --- | --- |
| 关于我 | `/about` | 身份、经历、建站缘起、联系 |
| AI 与产品 | `/ai` | AI × 硬件 × 行业系统的实践与合作方向 |
| 寻找苏开元 | `/sukaiyuan` | 旗舰叙事专题入口 |
| 文章 | `/discover` | 可传播的长文与方法手记 |
| 联系合作 | `/about#contact` | 邮箱、微信二维码和私密留言 |

这是正确的方向。一级导航不应再塞入 Wiki、查档、版本台账、权利护照等研究或站主功能。

### 3.2 苏开元专题的两层结构

`ProjectSectionNav` 已将专题内部导航分为两层：

**读者层（直接露出）**

`项目首页` → `从故事开始` → `人物群像` → `关系图` → `原件阅读` → `小说`

**研究层（“继续研究”下拉）**

`故事与原文对照`、`人物与事件 Wiki`、`查档现场`、`研究专题`

这套结构应继续坚持：普通读者能完成一次完整阅读，研究者能自行深入，但两者不会互相打断。

### 3.3 路由分层图


## 5. 当前视觉语言与组件规则

### 已确立的视觉方向

- **底色**：暖灰纸张 `#F3EFE7`，避免仿古做旧和“档案馆后台”感；
- **主色**：暗朱红 `#8B312B`，用于行动、关键年份、来源线索；
- **辅助色**：深墨绿／炭黑 `#202827`，用于大段叙事、作品区、页脚；
- **字体**：中文宋体／衬线用于大标题、引文、历史感；无衬线用于说明、产品信息和导航；
- **版式**：编辑式大标题、克制留白、细边框、编号与引文，不使用传统 SaaS 仪表盘卡片堆叠；
- **图像**：肖像、经授权的史料局部、原创系统示意图；不生成伪历史照片，也不拿第三方图片填满页面。

### 可复用的主组件

| 组件 | 用途 | 使用原则 |
| --- | --- | --- |
| `SiteHeader` / `SiteFooter` | 全站身份、导航、联系与边界 | 不增加研究工具到 Header。 |
| `ProjectSectionNav` | 苏开元专题二级导航 | 读者层优先，研究层收进“继续研究”。 |
| `ArchiveStoryCard` | 档案“阅读瞬间”卡片 | 先给人和问题，研究编号作为轻量尾注。 |
| `ArchiveEvidenceViewer` | 单一来源阅读台 | 支持局部、定位、主张、原馆入口；不嵌入整份原件。 |
| `SourceCard` | 目录中的来源卡 | 把载体、范围、编号等技术信息收进“研究定位”展开区。 |
| `RelationGraph` / `ResearchGraphExplorer` | 故事图谱与审计图谱 | 不把 Legacy、候选身份自动当作可靠事实。 |
| `NovelReader` / `ChapterComments` | 小说阅读与评论 | 页图水印只提高复制成本；评论必须先审后显。 |
| `FamilyHistoryDiagnostic` | 五题家族史起步诊断 | 答案只在页面内存，不接收文件和自由文本。 |
| `MediaStudioClient` | 媒体素材审稿包 | 只能生成 `review_only`，不得直接发布。 |

全局样式在 `src/app/globals.css`。新增页面优先复用 `personal-*`、`story-*`、`article-*` 这三组现有版式类，避免另起一套视觉系统。

## 6. 内容、数据与叙事边界

### 6.1 三种内容不能混为一谈

1. **个人 IP 内容**：站主的职业经验、AI 判断、产品案例、旅行与生活表达；
2. **苏开元研究投影**：从审计数据中派生的人员、关系、来源和任务；
3. **文学创作**：小说、合理外推、合成角色与戏剧结构。

文学可以让历史变得可读，但不能反向给研究数据“补事实”。家属回忆可以是写作火种与研究线索，但不应在网页中自动升级为公共史实。

### 6.2 图谱数据的三层

| 图层 | 规模 | 作用 | 绝不能做的事 |
| --- | ---:| --- | --- |
| 安全公开预览 | 5 来源、5 主张、7 节点、5 关系 | 页面基础事实投影 | 将同名记录拼成完整传记。 |
| 审计图谱 | 131 来源、211 主张、229 节点、127 关系 | 研究模式、Wiki、人物策展 | 跳过 `claim → source → locator` 回溯。 |
| Legacy 线索 | 107 节点、151 关系、258 映射 | 旧材料的检索与对照 | 自动迁移、自动合并身份、默认展示为事实。 |

权威材料入口是 `AI网站媒体/02-史料公开层/公开导出/authority-v1/CURRENT`；工程中的研究投影入口是 `src/data/research.json`，图谱文件位于 `public/data/graph/`。所有数据更新必须先通过生成与校验脚本，不能手改展示 JSON 来“让页面看起来更完整”。

### 6.3 可写的故事，不可偷换的结论

当前最稳的故事锚是 1936 年朱自清《绥行纪略》平地泉段落；页面可说明它记下了“留守司令蘇開元團長”、日期、地点和一次会面。它不能独自证明这位记录对象就是家族人物，也不能补写完整军旅履历、党籍、秘密任务或北平事件。

图谱、人物页、专题、小说伴读和媒体素材都必须保留这个边界。对普通读者，边界用自然语言表达；对研究读者，必须能回到来源定位。

- 浏览器内媒体素材审稿包：小红书、短视频、公众号、朋友圈、B 站／YouTube 模板。

### 明确未开放

- 公网部署、搜索引擎收录、公开发布；
- 账号注册、云端数据库、文件上传、外部模型处理；
- 支付、打赏、自动发帖、平台 OAuth、媒体直发；
- 将读者评论、留言或自动命中直接写回史料库；
- 原始 DOCX／PDF、家属私密材料、管理员令牌、运行日志进入 Git 或浏览器。

当前所有外部释放门禁均为关闭状态：`must_not_deploy=true`、`deployment_authorized=false`、全站 `noindex/nofollow`。这不是文案提示，而是运行层、构建校验、响应头与数据合同共同限制。

## 8. 工程运行方式

### 技术结构

- Next.js 16 App Router + React 19 + TypeScript + Tailwind CSS 4；
- 只能使用 `pnpm`；
- 普通页面仍由 Next.js 处理；
- 本机互动不使用 `src/app/api` 路由，而是由 `src/server/local-preview-runtime.ts` 内的单一 Node 请求处理器接管；
- 私密数据写入 `private-runtime/`，此目录被 Git 忽略，权限应保持目录 `0700`、文件 `0600`。

本机互动端点包括：匿名分析、私密留言、小说评论／审核、站主收件箱、语料命中索引和查档行动只读台。它们都只允许回环访问，且由同一运行层统一加上无缓存、无索引、CSP 和同源安全响应头。

### 常用验证顺序

以下命令都在工程根目录执行：

```bash
# 先做局部类型与样式检查
pnpm ts-check
pnpm lint:build
pnpm lint:style

# 校验各类数据合同
pnpm data:verify
pnpm graph:verify
pnpm evidence:verify
pnpm people:verify
pnpm family-history:verify
pnpm missions:verify
pnpm rights:passports:verify
pnpm media:verify
pnpm status:verify
pnpm security:verify

# 正式构建与完整本机冒烟测试
pnpm build
pnpm smoke:local
```

本机审阅地址的目标是 `http://127.0.0.1:3217`。当前机器曾配置一个仅回环的 LaunchAgent 来维持预览；若需要人工启动，应使用 `DEPLOY_RUN_PORT=3217 pnpm start`，并确认首页、`/sukaiyuan`、`/archives`、`/graph`、`/novel` 等路由实际返回内容后再开始视觉审查。

**不要**把本机预览地址、构建通过、私有 Git 仓库推送或 Coze 工程存在，描述为“已经公开上线”。

## 10. 推荐的后续开发路线

### 优先级 0：先把“可稳定审查”恢复到可重复状态

1. 处理 V1.3 候选版门禁，或明确把候选版从当前工程验证链中隔离；
2. 恢复并验证本机预览的真实 HTTP 可达性；
3. 以手机、平板、桌面三档重新检查本轮“档案故事化”改版；
4. 单独提交本轮 UI 改版，并记录截图／验收结果。

### 优先级 1：让个人 IP 内容真正长起来

现有网站的架构已经足够，但内容库存仍偏薄。下一批应该优先产出：

- 3—5 篇 AI × 硬件／支付／线下系统的真实案例或方法文章；
- 1 个“我怎样用 AI 做这座网站”的公开构建日志；
- 1 个可被潜在合作方快速理解的服务或共创案例页；
- 每篇长文对应的小红书、视频口播、公众号和朋友圈版本，但先在审稿包中人工复核。

内容的目标不是堆“AI 技巧”，而是持续证明：站主懂真实设备、系统、交付和行业现场。

### 优先级 2：把专题做成连续追更体验

建议按“一个可读故事 + 一张关系图 + 一页材料 + 一个下一步问题”的固定单元持续更新：

1. 1936 平地泉（已具备）；
2. 1933 任命记录；
3. 1942 编成表与李大超同框；
4. 人物群像中的李英夫、朱自清、傅作义；
5. 查档现场的真实进展。

每一单元都应允许读者停在故事层，也能一路走到来源层；不要把尚未闭环的真人身份和行动写成定论。

### 优先级 3：为将来公开版单列一条发布路线

公开版不是把当前本机站点直接部署。需要单独完成：

- 站主头像、微信二维码、邮箱和职业资料的公开授权确认；
- 小说、家属材料、扫描件、地图、第三方图片的逐项权利处理；
- 评论、留言、统计、隐私政策、滥用处理和数据留存策略的公网版改造；
- 域名、备案／法律咨询、内容审核与人工发布流程；
- 明确哪些栏目对外开放，哪些继续只作为站主工作台。

在这些条件满足前，媒体矩阵应仍然以“导出后人工发布”为准，不连接平台自动发帖。

## 11. 给下一位协作工具的不可违反清单

- 不得把家属资料、原始小说 DOCX／PDF、私密运行数据、管理员令牌或绝对路径提交到 Git；
- 不得将 Legacy 图谱、网络二传、OCR、小说片段或读者评论自动变成真人事实；
- 不得把同名、同地、同机构或同时代活动写成私交、组织关系或秘密任务；
- 不得为“看起来完整”而伪造人物肖像、史料原件或来源引文；
- 不得取消 `must_not_deploy`、`deployment_authorized=false`、回环监听、`noindex` 等门禁来完成“发布”；
- 不得重置、覆盖或删除现有工作树中的未提交故事化改版；
- 不得未经人工审查将内容直接发布到小红书、抖音、公众号、视频号、快手、B 站或 YouTube；
- 不得用“研究完成率”包装数据条数、查档任务数或图谱节点数。
