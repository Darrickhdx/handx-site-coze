# 新项目采用 Matt Pocock skills 指南

## 推荐的最小组合

对有真实用户、权限、数据边界或部署风险的项目，推荐最小组合：

1. `setup-matt-pocock-skills`
2. `grill-with-docs`
3. `domain-modeling`
4. `codebase-design`
5. `to-spec`
6. `to-tickets`
7. `implement` + `tdd`
8. `code-review`
9. `handoff`（只在真实交接时）

网站项目再加 Sites 本地构建/托管技能；只有部署授权明确时才进入 hosting。

## 推荐顺序与停止门禁

### 阶段 0：只读盘点

- 确认仓库、当前分支、脏文件、运行方式、验证命令和部署授权。
- 建立基线提交或其他可恢复检查点。

**停止门禁：** 不知道哪些变更属于用户、没有可恢复点、或部署授权不清楚时，不进入写入。

### 阶段 1：Grill

- 一次只问一个会改变方案的问题。
- 优先确认：解决哪个领域问题、谁使用、外部合同、主要测试 seam、明确不做什么。

**停止门禁：** 领域名称、外部入口或行为边界仍有两个合理答案时，不写规格。

### 阶段 2：领域与设计

- 把统一术语写入 `CONTEXT.md`。
- 重要决定写 ADR。
- 用 Design It Twice 至少比较两个真实可行接口，选择最难误用的一个。

**停止门禁：** 如果方案只能靠“开发者记得正确调用”保证安全，继续设计。

### 阶段 3：规格与任务

- `to-spec` 写问题、方案、用户故事、实施决定、测试决定、Out of Scope。
- 建立量化 scorecard 和硬门禁。
- `to-tickets` 拆成可独立验证的纵向切片，标出依赖。

**停止门禁：** 任务只有“先建数据层、再建 API、最后测试”这类横向切片时，重新拆分。

### 阶段 4：实施与 TDD

- 对已确认的 seam：一条失败测试 → 最小实现 → 变绿 → 小提交。
- 经常运行单测与类型检查；结束时跑完整验证。
- 不为只有一个实现的文件系统、时钟或存储建立公开 adapter。

**停止门禁：** 红灯不是由缺失行为造成、测试只能观察内部函数、或修复要求扩大 Out of Scope 时，退回规格。

### 阶段 5：双轴审查

- 固定审查点为“规格完成、实现未开始”的提交。
- Standards 与 Spec 分开审查。
- 每条发现只能是：已修复、带理由接受、或明确触发条件后处理。

**停止门禁：** 任一 Spec 阻断项、隐私/权限泄漏、公开内容越界或部署门禁失败时，不宣告完成。

### 阶段 6：交付与复盘

- 运行完整 validate、build、真实 smoke。
- 填写 scorecard；分数和硬门禁分开判断。
- 记录哪些 skill 真正改变了结果、哪些只增加了流程成本。
- 网站只有在授权明确、稳定 URL 和访问验证完成后才算部署交付。

## 何时缩短流程

- 单文件、低风险、可逆的小修：可用 `to-spec` 的简版说明 + 一条 TDD + review。
- 纯文案且无事实/权限边界：可跳过领域建模和 Design It Twice。
- 高风险数据、认证、支付、历史证据或公开发布：不要缩短硬门禁。

## 每个新项目可复制的检查表

- [ ] 当前证据和部署授权已确认
- [ ] 有基线回滚点
- [ ] 领域术语与外部合同明确
- [ ] 至少比较两个接口设计
- [ ] Spec 有明确 Out of Scope
- [ ] 任务是纵向行为切片
- [ ] 测试 seam 经确认且先红后绿
- [ ] 完整验证、构建、真实 smoke 通过
- [ ] Standards / Spec 双轴审查闭环
- [ ] 记分卡达标且所有硬门禁通过
- [ ] 未把本地预览误称为公开部署
